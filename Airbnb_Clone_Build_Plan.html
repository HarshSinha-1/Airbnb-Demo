Assumptions & Scope Decisions

The brief deliberately leaves some things open ("design your own schema", "auth may be simplified"). These are the concrete decisions this plan makes, stated explicitly so they can go straight into the README's "Assumptions" section.

Auth

Simplified/mocked: a lightweight session (signed cookie or JWT) created on a "Continue as guest / host" action, no password or email verification. A role field on the user determines whether the Host Dashboard nav item appears. Users can switch role in a dev-only account switcher for demo purposes.

Payments

Fully mocked. Checkout step shows a card-form UI (no real validation beyond format), a 1–2s fake "processing" state, then a confirmation screen. No payment provider is integrated.

Media

Listing photos are stored as URLs (either seeded stock photo URLs or user-pasted URLs on create/edit). No cloud upload pipeline in the MVP — "image upload to cloud storage" is listed as a bonus item only.

Map

Static approach for MVP: a location text + a static map image or embed (e.g. a non-interactive map tile) on the listing detail page. Interactive pins (Leaflet/Mapbox) are a bonus, not required for core functionality.

Messaging & Verification

Both are explicit "Coming Soon" placeholders — a disabled button/tab is sufficient, no backend needed.

Database

SQLite as specified, accessed via an ORM (SQLAlchemy if FastAPI) so the schema is portable to Postgres later without a rewrite.

A standard 3-tier architecture: Next.js frontend calls a FastAPI REST backend, which delegates to a thin service layer, which reads/writes SQLite through an ORM. No message queue or external services are needed — the brief explicitly allows everything to be mocked, so keeping this simple maximizes time spent on the parts that are actually evaluated (functionality, UI/UX, schema, API design, code quality).

Tech Stack

Frontend

Next.js 14 (App Router) + TypeScript · Tailwind CSS for Airbnb-style utility styling · a date-range picker library (e.g. react-day-picker) · react-hot-toast or similar for notifications · Headless UI or Radix for accessible modals/dropdowns.

Backend

FastAPI (Python 3.11+) · Pydantic models for request/response validation · SQLAlchemy ORM · Alembic (or a simple init_db.py) for schema creation · Uvicorn as the ASGI server.

Database

SQLite file-based DB for both dev and the hosted demo (simplest deployable option consistent with the brief's instruction). Schema written to be ORM-portable to Postgres later.

Infra / Deployment

Frontend → Vercel. Backend → Render or Railway (free tier), with the SQLite file persisted on a small disk/volume or re-seeded on boot. CORS configured on FastAPI for the deployed frontend origin.

Design notes

Why a join table for amenities

LISTING_AMENITIES is many-to-many so amenities are a controlled, filterable vocabulary (needed for the filter row) rather than a free-text field per listing.

Availability = derived, not stored

No separate "availability" table — a date range is blocked if it overlaps any BOOKINGS row with status = 'confirmed' for that listing. This avoids sync bugs between two sources of truth.

Reviews tied to a booking

booking_id on REVIEWS enforces "only guests who actually stayed can review" — matches the bonus requirement "leave a review after a completed stay" and is easy to relax later.

Price breakdown fields

nightly_price, cleaning_fee, service_fee_pct live on the listing so the price breakdown on the detail page and the booking summary compute from the same source.

Seed Data Plan

The brief requires the app to be "immediately usable" — seed script (backend/app/seed.py) run once on first boot (or via a make seed / npm script) should create:

  • 5–8 host users, each with a name, avatar, and a short bio.
  • 2–3 guest users for demoing "My Trips" and reviews with pre-existing history.
  • 20–30 listings spread across several cities, property types, and price points, each with 3–6 photos (stock URLs), 4–8 amenities, and realistic descriptions — enough variety to make filters and search meaningfully return different results.
  • A handful of existing bookings (some in the past, some upcoming) per listing so the availability calendar shows real blocked dates and "My Trips" isn't empty on first load.
  • A handful of reviews tied to past bookings so the reviews section and any rating aggregation has real content.

Booking & Availability Logic

sequenceDiagram participant U as Guest (frontend) participant API as POST /api/bookings participant SVC as BookingService participant DB as SQLite U->>API: {listing_id, check_in, check_out, guests_count} API->>SVC: validate(payload) SVC->>DB: SELECT bookings WHERE listing_id=? AND status='confirmed' AND date ranges overlap alt overlap found DB-->>SVC: conflicting rows SVC-->>API: 409 Conflict — dates unavailable API-->>U: show "these dates were just booked" toast else no overlap DB-->>SVC: [] SVC->>SVC: total_price = nights * nightly_price + cleaning_fee + service_fee SVC->>DB: INSERT booking (status='confirmed') DB-->>SVC: booking row SVC-->>API: 201 Created API-->>U: booking confirmation screen end

The overlap check is the one piece of business logic that must be correct: two ranges [check_in, check_out) overlap if new.check_in < existing.check_out AND new.check_out > existing.check_in. This single SQL condition, run inside the same transaction as the insert, is what guarantees "no overlapping/unavailable dates" from the brief — do this server-side, never trust client-side validation alone.

UI/UX Fidelity Checklist

The brief weighs visual similarity heavily ("should totally resemble Airbnb's design"). Concrete, checkable targets:

  • ☐ Rounded listing cards with a square/4:3 photo, heart icon top-right, title + location + rating + "$price / night" in the same visual hierarchy as Airbnb.
  • ☐ Sticky top nav with a centered rounded search pill (collapses to full search bar on scroll/click).
  • ☐ Category/filter row as horizontally scrollable icon pills below the nav.
  • ☐ Listing detail gallery as an asymmetric photo grid that opens a full-screen lightbox.
  • ☐ Booking card is sticky on desktop, becomes a bottom sheet / full-width CTA on mobile.
  • ☐ Consistent border-radius, spacing scale, and a red/pink accent color consistent with Airbnb's palette.
  • ☐ Toasts for booking success, listing saved/removed, form validation errors.
  • ☐ Empty states designed, not left blank (no bookings yet, no wishlist items yet, no search results).

Step-by-Step Build Phases

Ordered by dependency — each phase should be fully working (even if visually rough) before moving to the next, so the app is demoable at every stage. No calendar time is attached; work through them in order.

Phase 0

Project Scaffolding

  • Init frontend/ (Next.js + TS + Tailwind) and backend/ (FastAPI + SQLAlchemy) as siblings in one repo.
  • Set up database.py (engine/session), CORS in main.py, and a health-check route.
  • Set up api-client.ts on the frontend pointing at the backend base URL via an env var.

Done when: both dev servers run locally, frontend can hit /health and render the response.

Phase 1

Database Schema & Seed Data

  • Implement all ORM models from the ERD in models.py.
  • Write seed.py per the Seed Data Plan; make it idempotent (safe to re-run).

Done when: running the seed script produces a populated airbnb.db inspectable with a SQLite browser, matching the ERD's relationships.

Phase 2

Backend Core: Auth (mock) + Listings Read

  • Implement /api/auth/* mock session endpoints.
  • Implement GET /api/listings with all query-param filters and pagination, and GET /api/listings/{id} with nested photos/amenities/host/review-summary.

Done when: every filter/search combination the frontend will need is testable via /docs (FastAPI's auto Swagger UI) and returns correct, seeded data.

Phase 3

Backend Core: Bookings, Availability, Reviews, Wishlist, Host CRUD

  • Implement the overlap-safe booking creation from Booking & Availability Logic.
  • Implement availability, reviews, wishlist, and the full POST/PUT/DELETE /api/listings host-CRUD endpoints with ownership checks.

Done when: the entire API surface in API Reference is implemented and manually exercised via Swagger UI, including the "double-booking is rejected" case.

Phase 4

Frontend: Home / Explore + Search

  • Build <ListingCard/>, <ListingGrid/>, <SearchBar/>, <FilterRow/>, pagination/infinite scroll, wired to GET /api/listings.

Done when: a user can land on /, see seeded listings, search by location/dates/guests, apply filters, and page through results — all against the real backend, matching the UI/UX checklist for this page.

Phase 5

Frontend: Listing Detail Page

  • Build <PhotoGallery/>, amenities/description/host block, <AvailabilityCalendar/> (reads blocked ranges), price breakdown, <ReviewList/>.

Done when: navigating from a card opens a fully populated detail page with a calendar that correctly greys out seeded booked dates.

Phase 6

Frontend: Booking Flow + My Trips + Wishlist

  • Wire the booking summary card's "Reserve" action through the confirm modal → mocked checkout → confirmation screen → POST /api/bookings.
  • Build /trips against GET /api/bookings/mine, including a cancel action.
  • Wire the wishlist heart icon on cards/detail page to the wishlist endpoints and build /wishlist.

Done when: a full guest journey — search → detail → book → see it in My Trips → the listing's calendar now shows those dates blocked — works end to end with no page requiring a refresh to reflect state.

Phase 7

Frontend: Host Dashboard & Listing CRUD

  • Build /host (owned listings table + bookings list), and the shared <ListingForm/> used by both /host/listings/new and /host/listings/[id]/edit, including delete with a confirm step.

Done when: a host can create a listing from scratch, see it appear on the public Home page, edit it, and delete it, with the dashboard's booking list reflecting any bookings guests make against it.

Phase 8

Polish, Toasts, Empty States, Bonus Features

  • Pass over every page against the UI/UX checklist; add toasts and empty states everywhere they're missing.
  • Optional, time-permitting, in this order of payoff: responsive design, post-stay reviews, interactive map pins, superhost/rating badges, dark mode, cloud image upload.

Done when: the app feels cohesive and Airbnb-like across every screen, not just the ones built first.

Phase 9

Deployment & README

  • Deploy frontend/ to Vercel, backend/ to Render/Railway; run the seed script on the deployed backend; confirm CORS and env vars point frontend → deployed backend URL.
  • Write the README per the README Checklist.

Done when: the hosted link works standalone (no local backend needed), is pre-seeded, and the repo is public with both frontend/ and backend/ present.
